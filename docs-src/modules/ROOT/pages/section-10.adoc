= Section 10. Data Structures Selection in Practice

=== 10.1. Data Structure Selection Roadmap

Choosing an optimal data structure is a _multi-criteria decision problem_ that requires consideration of _functional requirements_, _data characteristics_, the _operation profile_, and _physical hardware constraints_. Functional requirements answer the question “What operations must be supported?”, the operation profile answers “How often and under what conditions will these operations be performed?”, and hardware constraints answer “What resources are available, and how do they affect performance?”

_Functional requirements_ specify which _operations on data_ a structure must support and which _properties_ it must preserve. Examples include _lookup by key_, _insertion and deletion of elements_, _access by index_, _maintaining sorted order_, and _retrieving values within a specified range_. These requirements establish the set of suitable data structures.

The _operation profile_ describes how a structure will be used: _which operations_ are performed most frequently, the _volume of data_ they involve, and their _sequence_. For example, one application may primarily perform lookups, with infrequent updates; another may continuously receive new elements and then process them sequentially. Even when the required operations are identical, differences in their _execution frequency_ may lead to the selection of different structures.

The **hardware constraints** of the system impose additional limitations on the choice of data structures. These constraints include the available RAM capacity, cache size and line size, memory access latency, memory bandwidth, pointer size and alignment requirements, parallel processing capabilities, and storage device characteristics. Each of these factors can significantly impact the performance of different data structures (Table 1).

Table 1. Hardware Characteristics and Constraints

[cols="1,3", options="header"]
|===
|Factor |Impact on data structure selection

|_Available RAM capacity_
|In addition to the data itself, a structure stores auxiliary information: pointers, indices, and reserved slots. This overhead may limit the maximum size of the structure.

|_Cache capacity and cache line size_
|Storing elements close together allows several adjacent values to be loaded in a single memory access and subsequently used without accessing RAM again.

|_Memory access latency_
|Particularly significant when following a chain of pointers: the address of the next element becomes available only after the previous element has been read.

|_Memory bandwidth_
|Limits the speed of bulk scanning, copying, and moving data, for example when inserting elements into an array.

|_Pointer size and alignment requirements_
|Affect the actual memory footprint of elements: pointers and alignment padding can substantially increase memory usage.

|_Parallel processing capabilities_
|When multiple cores are used, data partitioning and the frequency of access to shared memory become important. Contention over the same cache lines can reduce performance.

|_Storage device characteristics_
|When data does not fit in RAM, the number of storage accesses and the size of transferred blocks become important. This is one reason for using B-trees and B+ trees.
|===

> **Important:** The difference between register access time (< 1 ns) and RAM access time (~100 ns) is **two orders of magnitude**. In the time the CPU waits for data from RAM, it could have executed **hundreds** of operations. This is precisely why data structures that are "cache-friendly" outperform even those with better theoretical complexity.

=== 10.3.2. Key Concepts: Cache Line and Cache Miss

The CPU does not work with individual bytes but with fixed-size blocks called **cache lines** (typically 64 bytes). When a program accesses a variable, the entire cache line containing that variable is loaded into the cache.

* **Cache hit:** Data is already in the cache. Access takes ~1 ns.
* **Cache miss:** Data is not in the cache and must be loaded from RAM. Latency is ~100 ns (100× slower!).

**For data structures, this means:**

* **Arrays** (and any sequentially stored structures): When iterating over an array, the CPU loads one cache line (64 bytes = 8 elements of 8 bytes) and processes all 8 elements **without additional misses**. This achieves near-theoretical maximum speed.

* **Linked lists and trees:** Nodes are scattered randomly across memory. Moving to the next node almost always causes a **cache miss**, because the adjacent node does not reside in the same cache line. The latency accumulates, and performance degrades by a factor of 5–20.

=== 10.3.3. Prefetching Mechanism

Modern processors feature **hardware prefetchers** that analyze memory access patterns and proactively load data into the cache.

* For **arrays**, the prefetcher works perfectly: it detects linear traversal and begins loading cache lines **ahead**, before the program even requests them. This effectively hides RAM latency.

* For **linked lists and trees**, the prefetcher is **useless**: pointer-based transitions are unpredictable, and the CPU cannot anticipate where the program will jump next.

> **Conclusion:** If your data structure supports **sequential iteration** and you use it frequently in this mode, an array will be an order of magnitude faster than a tree or a list, even if the tree has O(log n) complexity and the array has O(n).

=== 10.3.4. Practical Rule: The "Cache Filter"

When selecting a data structure, **always** ask yourself three questions:

1. **Will the structure be iterated (traversed entirely) frequently?**
   * YES → Prefer arrays and vectors (even if insertion is O(n)).
   * NO → Trees and lists become viable options.

2. **What is the access pattern?**
   * Sequential (in order) → Arrays win due to prefetching.
   * Random (by index or key) → Hash tables and trees provide the advantage.

3. **How large is the data relative to the L3 cache size?**
   * Data fits in L3 (millions of elements) → The cache effect is maximized; structures with poor locality (lists) perform catastrophically.
   * Data does not fit in L3 (tens of millions) → The difference between arrays and trees becomes less critical because RAM is slow regardless.

=== 10.3.7. Bridge to the DRAKON Decision Diagram

Understanding the memory hierarchy enables the introduction of a **new critical filter** into the data structure selection algorithm (see the DRAKON diagram in Section 10.5):

* If **cache locality** is a priority (high-load systems, game engines, financial applications) → **favor arrays** and sequentially stored structures.

* If **cache locality** is not critical (background tasks, batch processing, infrequent access) → trees and lists can be chosen without concern.
